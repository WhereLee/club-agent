## 1.【P0 · S1】明文密码落 `oper_log`（高危，先做）

**现状**：`LogAspect.buildParams` 序列化整个入参落库；`/auth/register`、`/auth/login`、`PUT /user/password` 挂了 `@Log` → 明文密码在 `oper_log`，且 `/logs/oper` 对所有老师开放。

**待用户拍板（先报方案，勿动手）**：
- 方案 A：`LogAspect` 按字段名脱敏（字段名含 `password`/`secret` → 值替换为 `******`），改动集中在一处；
- 方案 B：DTO 密码字段加 `@JsonProperty(access = WRITE_ONLY)`，Jackson 序列化自动不输出，反序列化不受影响；
- 方案 C：三个认证接口摘掉 `@Log`（登录已有 `login_log` 审计）。
- 可组合（如 A 兜底 + B 精确）。**无论选哪个，存量清洗必做**。

**执行内容（拍板后）**：
1. 按所选方案实施代码修改；
2. 存量清洗：新建 `java/scripts/fix_oper_log_passwords.sql`，用正则把 `params` 列中 `"password":"[^"]*"`、`"oldPassword":"..."`、`"newPassword":"..."` 的值替换为 `******`（PG `regexp_replace`），脚本幂等；
3. 单测：`LogAspect` 脱敏行为（若走方案 A）：含 password 字段的 DTO 序列化后不含原值。

**验收**：
- 注册/登录/改密后查 `oper_log.params`，无任何明文密码；
- `mvn test` 全绿；
- `/logs/oper` 返回的历史数据中密码已掩码。

## 5.【P1 · C3】线程池隔离：AI 长任务与日志分池

**现状**：`logExecutor`（core 2/max 4/queue 500/CallerRuns）同时跑毫秒级日志和 40-120s 的 `SummaryServiceImpl.generate`，队列满时 CallerRunsPolicy 会把 `closeRecords` 请求线程拖住。

**执行内容**：
1. `AsyncConfig` 新增 `aiExecutor` bean：core 2 / max 2（LLM 调用并发无需大，防打满 Hikari）/ queue 50 / `AbortPolicy`；
2. `SummaryServiceImpl.generate` 的 `@Async("logExecutor")` 改为 `@Async("aiExecutor")`；
3. 拒绝策略配套：`generate` 提交被拒时不能让状态推进失败——`closeRecords` 里对 `summaryService.generate` 的调用捕获 `TaskRejectedException`，记 warn（`SummaryScheduler` 的定时重试会兜底，因 pending/failed 行已存在或下轮扫描补建；确认重试链路对被拒场景可覆盖，若不可则在 catch 内直接 upsert 一条 failed 行）；
4. 检查全仓其余 `@Async("logExecutor")` 使用点，确认只有日志类任务保留在 `logExecutor`。

**验收**：
- 单测：mock 场景下 `closeRecords` 在 generate 被拒时仍完成状态推进与 trace；
- `mvn test` 全绿。

## 6.【P1 · B1】recordDeadline 超时收口：待拍板

**现状**：`Activity.recordDeadline` 注释承诺"超时自动进总结"，`closeRecords` javadoc 写"超时扫描与手动共用"、预留了 `system=true` 入口，但**全仓没有扫描器**——截止后活动永远停在状态 7。

**待用户拍板（先报方案，勿动手）**：

**验收（方案 ② 时）**：造一个 `record_deadline` 已过期的状态 7 活动 → 一分钟内自动进入状态 8 且触发总结生成；`closeRecords` 并发双触发（调度 + 手动）只有一个成功（CAS 兜底）。

## 8.【P2 · C1】防重注解契约对齐：待拍板

**现状**：`RepeatSubmitAspect.finally { delete(key); }` 使 `intervalSeconds` 只在执行期生效，注解实际是"执行期互斥锁"，与"完成后 N 秒拒绝重复提交"的契约不符。

**待用户拍板（先报方案，勿动手）**：
- 方案 ①（真防抖）：删除 finally delete，靠 TTL 自然过期。**副作用提示**：状态机接口执行成功后，`intervalSeconds` 内的"重复请求"会从 1037（业务态已变）变为"请勿重复提交"文案——前端无感但语义变了；
- 方案 ②（承认现状）：保留实现，把 `@RepeatSubmit` javadoc 改写为"执行期并发互斥"，可考虑更名 `@ConcurrentGuard`（更名需全仓替换 25+ 处引用）。

**验收**：注解 javadoc 与实际行为一致；有至少一个单测描述该行为。
