### 1.2 安全问题清单

**S1【高危】明文密码落 `oper_log` 表**
- 位置：`LogAspect.buildParams` 把整个入参 DTO 序列化落库；`/auth/register`、`/auth/login`、`PUT /user/password` 三个接口恰好挂了 `@Log`。
- 后果：注册密码、登录尝试密码（含失败）、新旧密码全部明文可查；且 `/logs/oper` 接口对所有老师开放，等于老师可查全站密码。
- 修复方向（三选一或组合，修复前讨论）：
  1. `LogAspect` 按字段名脱敏（`password`/`secret` 前缀打码）——改动最小，依赖命名纪律；
  2. 三个认证接口摘掉 `@Log`（登录本来有 `login_log` 审计）；
  3. DTO 密码字段加 `@JsonProperty(access = WRITE_ONLY)`，Jackson 序列化自动不输出。
- 附带动作：**存量 `oper_log` 数据清洗**（UPDATE 掩码）。

**S2【中】Swagger/Knife4j 生产环境暴露**
- `springdoc.api-docs.enabled: true`、`knife4j.enable: true` 在公共 `application.yml`，`application-prod.yml` 未覆盖 → 生产匿名可见完整 API 面。
- 修复：prod profile 覆盖为 false。

**S3【中】K29 修复不对称：STOMP 通道漏了兜底**
- `AuthChannelInterceptor.authenticate` 第 98 行 `redisTemplate.hasKey()` 未包 try-catch，Redis 抖动时 WS CONNECT 异常冒泡。方向上仍是拒绝（安全），但与 HTTP 侧"保守拒绝 + warn 留痕"行为不一致。

**S4【中】预设老师账号弱密码兜底**
- `PRESET_TEACHER_PASSWORD` 默认值 `teacher123456` 明文在 `application.yml`（已入 git）；`DataInitializer` 创建后不强制首次改密。老师手握概念批复权 + 全站日志查看权（叠加 S1 后风险放大）。
- 修复：prod profile 启动时检测密码等于默认值即 fail-fast；配合"首次登录强制改密"。

**S5【中】Python 服务信任边界单薄**
- 身份透传设计正确（权限在 Java），但 Python 侧对转发的 `Authorization` 头无条件信任，唯一防线是监听 `127.0.0.1:8094`。部署失误绑到 `0.0.0.0` 即失守。
- 修复：加内部共享 secret 头（Java 发出、Python 校验），约 20 行代码。

**S6【低】注册接口缺 IP 维度限流**
- `/auth/register` 只有 `@RepeatSubmit(3s)`（key 含参数，换参即绕过），可批量刷账号。登录有 `@RateLimiter` 而注册没有，不对称。

**S7【低·预留条款】`/uploads/**` 匿名白名单**
- 当前只存头像（图片 + UUID 不可枚举），影响可忽略。但为 `permitAll` 全局放行，**将来新增文件类业务类型前必须重审此白名单**。

**S8【低·已知取舍】401/403 返回 HTTP 200 + 业务码**
- 与前端统一 `R.code` 风格一致（若依风格），刻意设计；对 WAF/网关按状态码识别不友好。记录在案，不返工。

## 二、业务一致性审查（状态机 ↔ 设计文档）

### 2.1 达标项

- 活动状态机主链 `1公示 → 2问卷 → 3讨论 → 4已发布 → 5报名 → 6执行 → 7留痕 → 8总结 → 9归档`，旁路 `10取消`，全部走**条件 SET CAS**（`WHERE status=前置态` + `clubId` 归属），`update=0` 统一翻译 1037，流转必留 trace（单出口 `trace()`），与设计文档第二章一致。
- 概念审批子流程（起草→两票→复议→老师批复→36h 超时作废）与设计文档第一章一致，超时走 `@Scheduled` 主动扫描（文档明确要求"定时任务而非懒判断"，实现符合）。
- 讨论群只读闸门：`ChatServiceImpl.send` 校验 `status=3 且 discussionClosedAt=null`，发布/取消后自动只读。
- 问卷"不感兴趣"惩罚机制落点在报名拦截（`SignupServiceImpl.isNotInterested`），在线协助放行 + 通知发起人，与设计文档惩罚机制条款一致。
- 唯一约束全覆盖：`uk_activity_signup`、`uk_form_submission_template_user`、`uk_activity_attendance`、`uk_activity_summary` 等，并发兜底不依赖应用层先查后写。

### 2.2 问题清单

**B1【中·需拍板】`recordDeadline` 超时自动进总结：注释承诺了，调度不存在**
- `Activity.recordDeadline` 字段注释："超时自动进总结阶段"；`ActivityService.closeRecords` javadoc："超时扫描与手动共用"；`closeRecords(clubId, id, userId, system=true)` 系统入口也预留了。
- 但全仓 `@Scheduled` 只有三个：概念 36h 扫描、总结失败重试、checkpoint 清理——**没有任何任务扫描 `recordDeadline`**。
- 实际行为：留痕截止只挡提交入口（`RecordServiceImpl.submit` 第 67 行），截止后活动永远停在状态 7，等发起人手动关闭留痕。
- 两条路二选一：① 业务上就是手动收口 → 修注释与 javadoc，删 `system` 参数死代码；② 确实要自动收口 → 补 `@Scheduled` 扫描器（模式照抄 `ConceptServiceImpl.scanTimeout`）。

**B2【低】`Activity` 实体类注释漂移**
- 类头注释与 `status` 字段注释仍写 "4=已发布 5=已取消"，实际常量 5=报名中、10=已取消（状态机从 5 态扩到 10 态时注释没跟）。注释漂移是屎山第一信号，随手修。

## 三、并发与可靠性审查

### 3.1 达标项

- 所有状态推进 = 单条条件 SET（原子），无读-改-写分裂；并发冲突（影响 0 行）统一拒绝而非覆盖。
- 乐观锁双要件齐备：`@Version` + `OptimisticLockerInnerInterceptor`（K13 教训已落实）。
- 限流/防重/失败计数全部 Lua 原子（INCR+EXPIRE 单脚本），无 check-then-act 窗口。
- `SummaryScheduler` 独立类承载 `@Scheduled`（避开 JDK 动态代理限制），注释写明了原因；失败重试有 `MAX_RETRY` 上限 + 手动重生成兜底，upsert 主键冲突已修（K32）。

### 3.2 问题清单

**C1【中】`RepeatSubmitAspect` 的 finally-delete 架空了 `intervalSeconds`**
- 执行完成后 `finally { redisTemplate.delete(key); }` → 注解实际语义是"执行期互斥锁"，而非"完成后 N 秒内拒绝重复提交"。注解 javadoc 承诺的防抖窗口只在请求执行期间生效。
- 对状态机接口伤害小（CAS 兜底），但**注解契约与实现不符**——后来人会按契约使用它。
- 修复二选一：① 去掉 finally delete，靠 TTL 自然过期（真防抖）；② 保留现状但把注解语义改写为"并发互斥"并更名（如 `@ConcurrentGuard`）。

**C2【中】Redis 故障无降级策略，三个切面行为不一致**
- `RateLimiterAspect` / `RepeatSubmitAspect` Redis 异常直接冒泡 → 接口 500；登录验证码与失败计数也硬依赖。K29 只给黑名单加了兜底。
- Redis 是全局单点：挂掉 = 登录、全部写接口不可用。fail-closed 本身是合理选择（安全优先），但**三处行为应统一 + 留痕**，并写进部署手册（Redis 高可用要求）。

**C3【中】`logExecutor` 线程池混用：日志与 AI 长任务共池**
- `AsyncConfig.logExecutor`（core 2 / max 4 / queue 500 / CallerRunsPolicy）既跑 `saveLoginLog`/`OperLogService` 毫秒级任务，又跑 `SummaryServiceImpl.generate`（调 Python，单次 40-120s 阻塞）。
- 后果：多个活动同时进总结阶段 → 4 线程被 LLM 调用占满 → 日志任务积压 → 队列满后 CallerRunsPolicy 让**请求线程**同步跑总结 → `closeRecords` 接口阻塞 120s，"异步不阻塞状态推进"的承诺失效。
- 修复：拆 `aiExecutor`（小池、AbortPolicy + 失败落库等调度重试）与 `logExecutor` 隔离。

### 4.2 问题清单

**Q1【中】"活动归属校验" 在 4+ 个类中重复实现**
- `getOwned(clubId, activityId)` 在 `ActivityServiceImpl` / `ActivityFileServiceImpl` / `SignupServiceImpl` / `RecordServiceImpl` 各写一份；`briefOf`/`isBlank` 两个类近乎逐字重复；`approvedMembers`、`nicknameOf` 各 2-3 处。
- 这是屎山的起点：归属校验规则一旦变化（如"已归档活动按社团可见"）要改四处。
- 修复：抽 `ActivityOwnership` 组件（或 service 基类），`getOwned` + `requireOwner` + `notifyAllMembers` 收口。

**Q2【低】RestClient 懒初始化两种写法并存**
- `ConceptAiServiceImpl.python()` 无同步（竞态下重复建实例，无害）；`SummaryServiceImpl.python()` 是标准 DCL。同一模式两种风格，统一为 DCL。

**Q3【中】测试覆盖偏科**
- Java 29 个用例仅覆盖 `ActivityServiceImpl`（15，质量高：CAS/权限/并发影响 0/快照聚合全覆盖）+ `ChatServiceImpl` + `RewardServiceImpl`；`SummaryService`（含 K31-K35 修复区）、`SignupService`、`RecordService`、`ConceptService`、`MembershipService` 均无单测。
- `scripts/smoke_*` 覆盖全链路但依赖真实服务器与种子数据，**不可进 CI、不可重放**。
- 建议优先级：`SummaryServiceImpl`（跨语言 + 状态多）> `ConceptServiceImpl`（并发修复密集区）> Signup/Record。

**Q4【低】`DuplicateKeyException` 翻译靠错误消息文本匹配**
- `handleDuplicate` 用 `e.getMessage().contains(约束名)` 识别——约束改名时翻译静默失效（退化为通用文案），无测试保护。可接受但需知晓。
